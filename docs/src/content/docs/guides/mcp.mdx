---
title: Use CoCo through MCP
description: Let an MCP-capable application inspect or continue workspaces in one repository.
---

Connect an assistant or application to inspect your workspaces, read agent
updates, and optionally send instructions. CoCo provides an MCP (Model Context
Protocol) server so compatible applications can use these tools.

## Before you begin

Start `cocod` in one terminal:

```bash
cocod
```

Then register the repository from another terminal if you have not already:

```bash
coco repo add /absolute/path/to/project
```

Use an absolute repository path in MCP configuration so behavior does not
depend on the directory from which the host starts.

## Configure an MCP host

Set the server command to `coco-mcp` and pass the repository as arguments. A
typical JSON-based host entry looks like this:

```json
{
  "mcpServers": {
    "coco": {
      "command": "coco-mcp",
      "args": ["--repository", "/absolute/path/to/project"]
    }
  }
}
```

Hosts use different configuration filenames and sometimes different outer
keys, but the command and argument list stay the same.

### Configure Codex as the host

For Codex, add a standard input/output server to `~/.codex/config.toml`:

```toml title="~/.codex/config.toml"
[mcp_servers.coco]
command = "coco-mcp"
args = ["--repository", "/absolute/path/to/project"]
```

The equivalent standalone command is:

```bash
coco mcp serve --repository /absolute/path/to/project
```

## Available tools

The repository is fixed when the server starts. By default it offers only
read-only tools:

| Tool                | What it does                                |
| ------------------- | ------------------------------------------- |
| `workspaces.list`   | List workspaces in the repository           |
| `workspaces.status` | Show the current state of one workspace     |
| `workspaces.diff`   | Show changes made by one workspace          |
| `turns.get`         | Check the outcome of one specific send      |
| `workspaceCreations.get` | Recover a workspace creation receipt |
| `workspaceDeletions.get` | Recover a workspace deletion result |
| `signals.types`     | Discover signal definitions and permissions |
| `signals.list`      | Read retained updates from agents           |

Read-only does not mean content-free: the connected host can see workspace
metadata, repository paths, diffs, and saved signal payloads. Enable the
server only in hosts you trust with that information.

## Allow creation

Add `--allow-create` only for an application trusted to create local checkouts
and configure worker tool processes. This adds `workspaces.create` without
granting message sending or interruption. Creation prepares a permanent
workspace with fresh or repository-local forked context; it does not start a model turn.

See [Create workspaces from an application](../../reference/workspace-setup/)
for inputs, safe retries, receipt lookup, and fixed worker MCP configuration.

## Allow messages

Add `--allow-send` only when the MCP host should be allowed to start another
Codex turn:

```json
{
  "mcpServers": {
    "coco": {
      "command": "coco-mcp",
      "args": ["--repository", "/absolute/path/to/project", "--allow-send"]
    }
  }
}
```

This adds `workspaces.send`. Any connected host can then start the first or a
later turn under that workspace's Codex permissions and account usage. Leave
it disabled unless that is the access you intend to grant.

## Ask the user before changes

For an interactive host, add `--confirm-changes` to show a CoCo-generated
review before creation, sending, interruption, closing, reopening, or deletion.
The corresponding `--allow-*` grants are still required. Ordinary MCP setup
does not ask questions unless this option is present.

The host must support MCP form elicitation. Confirmation defaults to No and
expires after five minutes. A declined or cancelled review returns
`CONFIRMATION_CANCELLED`; an unsupported host, lost response, or timeout
returns `CONFIRMATION_UNAVAILABLE`. Neither dispatches the action. Reviews
over 16 KiB return `CONFIRMATION_TOO_LARGE`; use an ordinary CoCo command for
those messages. After acceptance, normal operation and retry rules apply.

`coco ai` enables these reviews automatically. See
[Natural-language control](../ai/) for its optional automatic mode.

## Allow cleanup

Grant only the actions your application needs:

```bash
coco-mcp --repository /absolute/path/to/project --allow-close --allow-reopen --allow-delete
```

This adds `workspaces.close`, `workspaces.reopen`, and `workspaces.delete`.
Closing frees the checkout while preserving work for later. Deletion removes
the workspace and its associated resources, with explicit options to keep the
conversation or branch. Active work and unsafe data loss remain protected.

For deletion previews, recoverable operation IDs, and safe retries, see
[Clean up from an application](../../reference/workspace-lifecycle/).

## Track a specific send

An application can supply an `operationId` to `workspaces.send`, then use
`turns.get` with that same key and workspace to track its outcome, even if the
start response was lost. A workspace becoming Ready alone does not tell you
whether that send succeeded, failed, or was interrupted.

Add `--allow-interrupt` to expose `turns.interrupt`. This permission is separate
from `--allow-send`. Strict interruption is the default and remains unavailable
with current Codex. A caller can explicitly choose `mode: "bestEffort"` to
request a native interrupt, accepting that a concurrently started newer turn
could be interrupted instead. Repeats inspect the saved attempt rather than
sending again; only the original turn's `interrupted` outcome confirms its stop.

See [Track a turn](../../reference/turns/) for exact inputs, responses,
supported Codex version, and recovery guarantees.

## What this integration controls

To let a Codex workspace publish structured updates, select schema files with
`--signal-catalog DIR` and grant specific versions with `--allow-emit NAME@VERSION`.
See [Publish agent updates](../signals/) for setup and
[Signal reference](../../reference/signals/) for publication permissions.

This MCP server lets another application inspect and control CoCo workspaces.
Configure tools that should be available _inside_ a Codex workspace through
its selected Codex profile or an application's fixed worker MCP binding.
Those settings are separate from the tools `coco-mcp` exposes to its host.
