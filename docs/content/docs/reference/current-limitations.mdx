---
title: Troubleshooting and limitations
description: Resolve common CoCo alpha problems and understand its current boundaries.
---

CoCo is alpha software for supervised local use. Start with the checks below
when a command does not behave as expected.

## CoCo cannot connect

Run `cocod` in another terminal and leave it open:

```bash
cocod
```

With the default paths, only one coordinator should run for your user. If a
second instance says another process already owns CoCo, keep using the first
one.

## Codex cannot be started

Check the Codex command that CoCo will find:

```bash
codex --version
```

This alpha is tested with `codex-cli 0.147.0`. If `codex` is installed outside
`PATH`, set its absolute path before starting `cocod` and before using `jump`:

```bash
export COCO_CODEX_BINARY=/absolute/path/to/codex
cocod
```

Set the same variable in the other terminal that runs `coco jump`, or add it
to your shell configuration so both commands inherit it.

A different Codex version may expose incompatible commands or App Server
behavior.

## Cargo cannot build CoCo

Cargo installation compiles native code locally. In addition to Rust 1.98.1
or newer, Linux needs a working C compiler and linker; macOS needs the Command
Line Tools. Nix installation supplies the project toolchain as an alternative.

## A repository is rejected

Workspace creation needs a Git repository with at least one commit and a clean
selected checkout. Inspect it with:

```bash
git status --short
git log -1 --oneline
```

Commit, move, or otherwise handle existing changes yourself before retrying.
CoCo never stashes or resets them for you.

## A workspace name is ambiguous

The same name can exist in different repositories. Retry with a leading
repository path:

```bash
coco ../api status fix/login
```

You can also use the full workspace ID shown by `coco --all-repos ls`; IDs
resolve from any directory.

## A workspace is already working

CoCo accepts another `send` only when the workspace is ready. It does not queue
messages behind an active turn. Follow the current one first:

```bash
coco status fix/login --follow
```

`Ready` means the thread is idle and can accept another message; it does not
mean the code was reviewed, merged, or otherwise complete.

## A named profile changed

After restarting `cocod`, CoCo verifies that a workspace's parsed named-profile
settings still match those used at creation. Restore the configuration at
`$CODEX_HOME/<name>.config.toml` or create a new workspace with a new profile
name. Comments and formatting may change; setting changes may not. CoCo will
not silently resume the old workspace with a different named overlay.

Codex's base configuration is not pinned by this check. Changing it can affect
settings that any resumed workspace does not override in its named profile.

## Local data and secrets

CoCo keeps workspace metadata, messages sent with `coco send`, completed agent
messages, and activity history in your local user data. Git changes remain in
the managed worktrees. Secret answers entered through `coco decide` are hidden
while typing and are not retained by CoCo.

An MCP host can receive repository paths, workspace metadata, and code diffs.
Configure `coco-mcp` only in applications you trust with that information.

## Current alpha limitations

- Keep `cocod` running while workspaces are active. Installation does not
  create or enable a background service.
- The shared Codex connection uses experimental App Server functionality.
- `coco decide` handles known command approvals, file-change approvals, and
  Codex questions. An unknown request type remains blocked instead of being
  answered unsafely.
- Prepared conversations can be loaded after restarting `cocod`, but a turn
  active during the restart is interrupted and does not continue
  automatically. A pending decision from the old process can no longer be
  answered.
- CoCo has no commands to cancel, complete, remove, merge, or clean up a
  workspace. Created branches, worktrees, and workspace records remain.
- A workspace fork requires a ready, clean source in the same repository and
  carries only committed code. New workspaces always create a
  `coco/<name>` branch.
- CoCo's MCP server can inspect or continue existing workspaces. CoCo does not
  currently provide its own MCP registry or per-workspace tool selector.

Review workspace changes before relying on them, and do not depend on active
work surviving a coordinator restart or on automatic cleanup.
