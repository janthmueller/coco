title: CoCo
description: Start Codex work, leave it running, and return to the exact workspace.
---

CoCo stands for **Codex Coordinator**. It is a local control plane that gives
each piece of Codex work a durable name and keeps its conversation, Git
worktree, repository, and settings together.

The workspace remains addressable after the CLI command or Codex terminal UI
that started it exits. You can inspect it from another terminal, answer a
request, send more work when it is ready, or reopen the same conversation in
the native Codex UI.

## When CoCo helps

Use CoCo when you want to:

- run several separate pieces of Codex work across one or more repositories;
- start work from a short-lived command and supervise its state and resource
  use separately;
- move between CLI commands, an MCP client, and the native Codex terminal UI
  without losing the exact conversation or checkout;
- prepare code and conversation context independently; or
- free a worktree and later restore it without losing the workspace;
- let an agent publish a validated update and react with a trusted local
  command.

Codex reasons, calls tools, requests approval, and edits files. CoCo
coordinates the environment around that work and keeps it reachable.

## The core workflow

| You want to…                                 | Use…                          |
| -------------------------------------------- | ----------------------------- |
| Prepare a separate workspace                 | `coco create`                 |
| Start or continue a Codex turn               | `coco send`                   |
| Check once or follow live state              | `coco status`                 |
| Answer a supported approval or question      | `coco decide`                 |
| Enter the same conversation in the Codex TUI | `coco jump`                   |
| Review changes from the workspace base       | `coco diff`                   |
| Free a worktree without losing the workspace | `coco close`                  |
| Restore or permanently retire closed work    | `coco reopen` / `coco delete` |

`coco` commands normally exit after returning their result. `cocod` stays
running and owns the active Codex process, so leaving `send`, `status
--follow`, or a TUI opened by `jump` does not by itself cancel a turn. Add
`--wait` to `send` only when that command should remain attached and print the
final response.

## What a workspace keeps together

A workspace has:

- one registered Git repository and a separate worktree;
- one persistent Codex thread after work begins;
- the model and Codex profile selected for that thread; and
- a fixed Git base plus the chosen conversation context.

The code base and conversation context are independent choices. You can start
from clean code on `main` while inheriting an investigation from another CoCo
workspace or an exact Codex thread ID. By default, CoCo starts fresh and
creates a `coco/<workspace>` branch.

## More than one terminal

The `coco` CLI is the main control surface. A local MCP server can expose the
same repository-scoped workspaces to another application; inspection is
read-only unless you explicitly enable sending. Agents can also publish
explicitly enabled structured signals for humans or integrations to read
later. CoCo hooks can run a local command after a matching saved signal or
workspace lifecycle change, while guards can stop a checked close or deletion.

<Callout type="warn" title="Alpha software">
  CoCo is intended for supervised local use on Linux and macOS. Keep `cocod`
  running while a turn is active and read the [troubleshooting and
  limitations](/docs/reference/current-limitations) before relying on it for
  important work.
</Callout>
